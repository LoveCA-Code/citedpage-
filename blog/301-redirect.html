먼저 결론부터

  1. 301 리다이렉트는 주소를 영구히 옮겼다고 알리는 정상 응답입니다. 오류가 아니니 고치려 하지 않으셔도 됩니다.
  2. 영구 이동이면 301, 되돌릴 수도 있으면 302를 쓰시면 됩니다. 구글은 301만 대표 주소를 바꾸는 강한 신호로 받습니다.
  3. 링크 가치는 새지 않습니다. 다만 순위가 돌아오는 데 몇 달이 걸리니 일정에 미리 넣으셔야 합니다.

301 리다이렉트란?

301 리다이렉트는 옛 주소로 들어온 방문자를 새 주소로 보내면서, 그 이동이 영구적이라고 알리는 응답입니다.1[1]구글은 이것을 “기존 URL을 다른 URL과 연결 지어 방문자와 Google 검색에 페이지의 위치가 새로 지정되었음을 효과적으로 알리는 방법”이라고 풀어 설명합니다. 알리는 상대가 둘이라는 점이 중요합니다. 고객에게는 화면을 옮겨 주고, 검색엔진에는 색인을 옮기라고 알리는 것입니다. 구글이 든 쓸 자리도 도메인을 옮길 때, 두 사이트를 합칠 때, 페이지를 지우고 다른 쪽으로 보낼 때 셋입니다.출처[1] Google 검색 센터 - 리디렉션 및 Google 검색 옛 주소에 붙여 두는 이사 안내문이라고 보시면 됩니다. 안내문이 없으면 옛 주소를 아는 고객과 검색엔진이 사라진 자리에 그대로 도착하기 때문입니다. 여기서는 리다이렉트라는 말의 뜻과, 301이 오류와 어떻게 다른지를 봅니다.

자동으로 다른 주소로 보내는 일

리다이렉트(redirect)는 들어온 주소에서 다른 주소로 자동으로 보내는 일입니다.2[2]네이버도 같은 말을 쓰는데 설명이 더 쉽습니다. “브라우저 주소 입력창에 www.mysite.com 주소를 입력했는데 www.mysite.com/home 처럼 조금 다른 주소로 접속되었다면 사이트 첫 화면에 리다이렉트가 설정된 것입니다.” 주소창에 넣은 것과 열린 것이 다르면 리다이렉트가 걸려 있다는 뜻이니, 내 사이트에 걸려 있는지는 이 방법으로 바로 보실 수 있습니다.출처[9] 네이버 서치어드바이저 고객센터 - 301 리다이렉트(redirect) 설정 소개 고객이 주소창에 옛 주소를 넣어도 화면은 새 주소로 바뀝니다. 고객이 따로 누를 것은 없습니다.

앞에 붙은 301은 그 이동이 영구적이라는 뜻입니다. 그래서 구글은 301이 걸린 옛 주소 대신 새 주소를 검색 결과에 보여 줍니다.3[3]영구라는 말은 규격에서 온 것입니다. RFC 9110은 301을 받은 쪽이 “any future references to this resource ought to use one of the enclosed URIs”, 앞으로의 참조는 새 주소를 쓰라고 명시합니다. 구글이 검색 결과를 바꾸는 것도 그래서입니다. 구글 문서는 영구와 임시를 “영구 리디렉션: 검색결과에 새 리디렉션 대상을 표시합니다” / “임시 리디렉션: 검색결과에 소스 페이지를 표시합니다”로 나눠 설명합니다. [7]출처[7] IETF RFC 9110 - HTTP Semantics[1] Google 검색 센터 - 리디렉션 및 Google 검색 되돌릴 생각이 있다면 301을 쓰시면 안 됩니다.4[4]구글이 영구 리디렉션 설명 칸에 조건을 하나 달아 두었습니다. “리디렉션을 되돌리지 않는다고 확신하는 경우에 영구 리디렉션을 사용합니다.” 되돌릴 때 곤란해지는 이유는 브라우저가 301을 저장해 두기 때문입니다. 규격도 301 응답을 캐시할 수 있다고 밝혀 두었습니다. 한번 301을 받은 브라우저는 서버에 다시 묻지 않고 바로 새 주소로 가므로, 서버에서 리다이렉트를 지워도 그 사람 화면에서는 한동안 그대로입니다. 301은 오류가 아닙니다

301은 오류 코드가 아닙니다. HTTP 규격에서 301이 속한 3xx 묶음의 이름은 이동(Redirection)입니다. 오류로 분류되는 쪽은 4xx와 5xx입니다.5[5]규격은 3xx를 “The 3xx (Redirection) class of status code indicates that further action needs to be taken by the user agent in order to fulfill the request.”라고 밝히고 있습니다. 요청을 끝내려면 한 걸음 더 가라는 뜻이지 실패했다는 말이 아닙니다. 구글도 오류로 보고하는 범위를 따로 쓰는데, 4xx와 5xx 범위의 상태 코드와 “실패한 리디렉션(3xx)에 관한 오류 메시지를 생성합니다”라고 되어 있습니다. 3xx 가운데에서도 실패한 것만 오류입니다. [7]출처[7] IETF RFC 9110 - HTTP Semantics[3] Google 크롤링 인프라 - HTTP 상태 코드가 Google 크롤러에 미치는 영향

그래서 서치 콘솔에서 “리디렉션이 포함된 페이지”를 보셔도 고치실 것이 없습니다. 다만 체인이 너무 길거나 돌고 도는 실패한 리다이렉트는 오류로 잡힙니다.6[6]서치 콘솔은 이 둘을 다른 자리에 보여 줍니다. 상태 쪽은 “다른 페이지로 리디렉션되는 비표준 URL입니다. 따라서 이 URL의 색인은 생성되지 않습니다”라고만 나와 있어 손댈 것이 없습니다. 오류 쪽에는 “리디렉션 체인이 너무 김”, “리디렉션 순환 오류”, “리디렉션 URL이 최대 URL 길이를 초과”, “리디렉션 체인에 잘못되거나 빈 URL이 있음” 네 가지가 따로 올라옵니다. 이 네 가지가 보일 때만 고치시면 됩니다.출처[4] Search Console 도움말 - 페이지 색인 생성 보고서 301 자체가 아니라 잘못 이어 놓은 것이 문제인 것입니다.

301과 302

302 리다이렉트는 같은 자리를 임시로 비웠을 때 쓰는 응답입니다.7[7]규격이 그렇게 정해 두었습니다. RFC 9110은 302를 “The 302 (Found) status code indicates that the target resource resides temporarily under a different URI.”로 정의하고, 바로 뒤에 “the client ought to continue to use the target URI for future requests”를 붙입니다. 돌아올 자리이니 앞으로도 옛 주소를 계속 쓰라는 뜻입니다. 301이 새 주소를 쓰라고 쓰는 것과 정반대입니다.출처[7] IETF RFC 9110 - HTTP Semantics 301이 이사 안내문이라면 302는 잠시 자리를 비운다는 쪽지입니다. 둘을 구분해 써야 하는 이유는 구글이 두 응답을 다르게 받기 때문입니다. 여기서는 구글이 둘을 어떻게 다르게 받는지와, 302를 둘러싼 오해 하나를 봅니다.

301은 강한 신호, 302는 약한 신호

구글 문서는 301과 302를 거의 같은 문장으로 설명하고 단어 하나만 다르게 밝혀 두었습니다. 301은 “강력한 신호”, 302는 “약한 신호”입니다.8[8]두 문장을 나란히 놓으면 차이가 보입니다. 301은 “Google은 리디렉션을 따르고 Google 시스템은 리디렉션을 리디렉션 대상이 처리되어야 한다는 강력한 신호로 사용합니다.” 302는 “기본적으로 Google 크롤러는 리디렉션을 따르고 Google 시스템은 리디렉션을 리디렉션 대상이 처리되어야 한다는 약한 신호로 사용합니다.” 앞부분이 똑같습니다. 둘 다 따라가고 둘 다 신호로 씁니다. 다른 것은 세기뿐입니다.출처[3] Google 크롤링 인프라 - HTTP 상태 코드가 Google 크롤러에 미치는 영향

세기가 다르면 결과가 달라집니다. 영구 이동에 302를 걸면 검색 결과에 옛 주소가 남습니다. 되돌릴 계획이 없다면 301을 쓰시면 됩니다.

302도 쌓아 둔 가치가 사라지지는 않습니다

업계 글에는 302가 가치를 넘기지 않는다는 설명이 많습니다. 저희가 읽은 16곳 가운데 7곳이 그렇게 썼습니다. 그런데 구글은 302도 따라간다고 설명하고, 존 뮬러는 오래 걸어 둔 302가 301에 가깝다고 했습니다.9[9]뮬러가 2022년에 남긴 글을 Search Engine Roundtable이 전합니다. 그는 302가 옛 주소를 그대로 두라는 뜻일 뿐 도착 페이지의 평판을 옛 주소로 끌어오지는 못한다고 말한 뒤, “Also, a longer-term 302 is more like a 301.”이라고 덧붙였습니다. 오래 두면 구글이 영구로 본다는 말입니다. 저희는 원래 게시물을 읽지 못해 이 매체의 보도로 확인했습니다. 16곳은 한국어 글 8곳과 영어 매체 8곳이고 2026년 10월에 세었습니다.출처[14] Search Engine Roundtable - Google On Redirect Pull Backs Plus Signal Consolidation (2022)

세기가 약한 것이고 0이 아닙니다. 그러니 영구 이동에 302를 쓰셨더라도 급하게 고치실 일은 아니고, 다음부터 301을 쓰시면 됩니다.10[10]그래도 구글은 상태 코드를 뜻에 맞게 쓰라고 당부합니다. “다른 클라이언트(예: eBook 리더기, 기타 검색엔진)가 리디렉션을 활용할 수 있도록 리디렉션에 적합한 상태 코드를 사용하세요.” 구글만 보고 고르지 말라는 말입니다. 같은 표에 307과 308도 있는데, 구글은 307을 302와 같다고, 308을 301과 같다고만 설명합니다. 다만 규격에서는 301이 POST 요청을 GET으로 바꾸는 것을 허용하고 308은 허용하지 않습니다. 검색에는 같고 동작은 다른 것이니, 주문이나 로그인처럼 POST를 받는 주소를 옮기실 때만 308을 쓰시면 됩니다. 링크 가치와 회복 기간

301로 옮기실 때 링크로 쌓은 힘이 빠져나가지 않습니다. 구글도 이 대목에 “링크 크레딧은 걱정하지 마세요”라는 제목을 달아 두었습니다.11[11]그 제목 아래 문장은 한 줄입니다. “301 및 기타 영구 리디렉션으로 인해 PageRank가 손실되는 일은 없습니다.” 영문판은 “301 and other permanent redirects don’t cause a loss in PageRank.”입니다. 사이트를 옮기는 사람이 가장 먼저 걱정하는 대목이라 따로 묶어 둔 것으로 보입니다. 페이지랭크(PageRank)는 구글이 쓴 단어를 그대로 옮긴 것입니다.출처[2] Google 검색 센터 - 사이트 이동 방법(URL 변경이 있는 경우) 그런데도 트래픽은 한참 안 돌아옵니다. 구글이 옛 주소를 가리키는 남의 링크를 하나씩 다시 읽어 새 주소로 옮겨 붙여야 하기 때문입니다. 여기서는 업계가 쓰는 비율 숫자와 실제 회복 기간을 봅니다.

90~99%도 15%도 출처가 없습니다

업계 글에 나오는 전달률 90~99%나 손실 15% 같은 숫자는 쓰지 마십시오. 출처를 따라가 보면 모두 비어 있습니다.12[12]저희가 읽은 16곳 가운데 7곳이 숫자를 밝혔습니다. 90~99%, 94% 이상, 약 70~90%, 95~99%, 손실 15%, 체인 한 단계당 5%입니다. 숫자끼리 맞지 않는 것부터 이상한데, 하나씩 따라가 보면 이렇습니다. 가장 오래된 15%는 2013년 맷 커츠의 영상에서 나왔습니다. 그런데 Ahrefs가 “Matt didn’t actually say that 301 redirects lost 15% of PageRank in that video. That was just the figure he used as an example.”이라고 설명합니다. 커츠가 실제로 한 말은 “The amount of PageRank that dissipates through a 301 is almost exactly, is currently identical to the amount of PageRank that dissipates through a link.”였습니다. 301이 따로 깎는 것이 아니라 링크를 하나 거칠 때 원래 줄어드는 만큼이라는 뜻입니다. Search Engine Journal도 “Cutts doesn’t say there is a specific percentage.”라고 안내합니다. 95~99%는 Conductor가 일반적인 합의라고만 쓴은 숫자이고 출처가 달려 있지 않습니다. 한국 글들이 Moz와 Ahrefs의 연구라고 붙여 쓴 90~99%는 Ahrefs 원문에 없었습니다. 저희가 그 글과 용어집을 받아 읽어 확인했습니다(2026년 10월 3일). 구글 문서 일곱 건에도 비율은 없습니다. 회복까지 중간값 304일

구글은 중간 규모 사이트도 새 주소가 옛 주소를 대신해 나오기까지 몇 주 이상 걸린다고 안내합니다.13[13]구글의 문장은 “일반적으로 중간 규모의 웹사이트의 경우 Google에서 이전 URL 대신 새 URL을 점진적으로 표시하는 데 몇 주 이상 걸릴 수 있으며, 대형 사이트의 경우 더 오래 걸릴 수 있습니다”입니다. 점진적으로라는 말이 핵심입니다. 어느 날 한꺼번에 바뀌는 것이 아니라 주소마다 따로 넘어갑니다. 속도는 “URL 수와 서버 속도에 따라 크게 달라집니다”라고 나와 있어, 서버가 느리면 더 오래 걸립니다.출처[2] Google 검색 센터 - 사이트 이동 방법(URL 변경이 있는 경우)

실제로는 더 걸립니다. 도메인 이전 1,052건을 모아 센 자료에서 90일 안에 트래픽이 돌아온 경우는 **22.8%**였습니다. 회복까지 걸린 기간의 중간값은 304일이었습니다.14[14]SALT.agency가 2026년 6월에 공개한 집계입니다. 누적 회복률을 날짜별로 보면 30일 5.1%, 60일 12.7%, 90일 22.8%, 180일 35.4%, 365일 59.5%, 730일 83.5%입니다. 1년이 지나야 겨우 절반을 넘습니다. 중간값과 평균은 “The median recovery time across the dataset is 304 days. However, the long tail means the mean is significantly higher at 489 days”로 나와 있습니다. 평균이 중간값보다 185일이나 큰 것은 아주 오래 걸린 사례가 섞여 평균을 밀어 올렸다는 뜻입니다.출처[13] SALT.agency - Only 27% of domain migrations recover in 90 days (2026) 3년이 지나도 돌아오지 못한 곳이 13.9% 있었습니다.15[15]표 아래 각주에 “did not show full traffic recovery signals after 3 yers”라고 나와 있습니다(원문에 오타가 있습니다). 이 숫자를 그대로 믿기 전에 네 가지를 함께 보셔야 합니다. 첫째, 동료 심사를 받은 연구가 아니라 대행사 자체 조사입니다. 표본을 자사 작업물과 업계에서 받은 사례라고 밝혔으므로 잘된 이전과 망한 이전이 고르게 담겼다고 보기 어렵습니다. 둘째, 글쓴이도 회귀 분석은 하지 않았다고 밝혔습니다. 무엇이 회복을 앞당기는지는 이 자료로 말할 수 없습니다. 셋째, 재는 기준이 순위가 아니라 월간 자연 검색 트래픽이어서 이전과 무관한 계절 변동이 섞입니다. 넷째, 그 글의 제목은 90일 27%인데 표의 90일은 22.8%이고 27.8%는 120일 칸 숫자입니다. 저희는 표의 숫자를 썼습니다. 업계 글의 다른 숫자들(트래픽 30~70% 감소, 12개월 내 80~100% 회복)은 한 곳씩만 쓰고 출처가 없어 쓰지 않았습니다.출처[13] SALT.agency - Only 27% of domain migrations recover in 90 days (2026)

겁주려고 쓰는 숫자가 아닙니다. 이전 일정에 몇 달을 비워 두시고, 리다이렉트는 최소 1년 두셔야 한다는 뜻입니다.16[16]1년은 구글이 적은 숫자입니다. “리디렉션을 최대한 오랫동안 유지합니다. 일반적으로 최소 1년입니다.” 왜 1년인지도 바로 뒤에 붙어 있습니다. “이 기간이 확보되어야 Google은 이전 URL로 연결되는 다른 사이트의 링크를 다시 크롤링하고 재할당하는 등 모든 신호를 새 URL에 전송할 수 있습니다.” 신호가 저절로 넘어가는 것이 아니라 구글이 남의 사이트에 걸린 링크를 하나씩 다시 읽어야 한다는 말입니다. 남의 사이트를 언제 다시 읽을지는 우리가 정할 수 없고, 그래서 시간이 걸립니다.출처[2] Google 검색 센터 - 사이트 이동 방법(URL 변경이 있는 경우)

301을 거는 방법

301은 서버에서 거는 것이 가장 낫습니다. 구글이 리다이렉트 방법을 올바르게 해석할 가능성이 높은 순서대로 늘어놓았고, 서버에서 거는 쪽이 맨 위이기 때문입니다.17[17]구글 문서는 방법을 표로 내놓으며 “순서는 Google에서 올바르게 해석할 가능성이 높은 순으로 되어 있습니다(예: 서버 측 리디렉션이 올바르게 해석될 가능성이 가장 높음)“라고 명시합니다. 영구 리디렉션 쪽 순서는 HTTP 301, HTTP 308, meta refresh(0초), HTTP 새로고침(0초), JavaScript location입니다. 사이트 이전 문서도 “가능하면 301, 308 등의 HTTP 영구 리디렉션을 사용하는 것이 좋습니다”라고 같은 말을 합니다. [1]출처[1] Google 검색 센터 - 리디렉션 및 Google 검색[2] Google 검색 센터 - 사이트 이동 방법(URL 변경이 있는 경우) 여기서는 서버에서 거는 법과, 실무에서 틀리는 자리 셋을 봅니다.

서버에서 거는 것이 가장 낫습니다

구글 문서가 실어 둔 예시도 한 줄짜리입니다.18[18]두 줄 모두 구글 문서에 실린 코드를 그대로 옮긴 것입니다. 손댈 파일은 “Apache의 .htaccess 파일” 같은 서버 구성 파일이고, PHP 같은 서버 쪽 스크립트로 헤더를 세워도 됩니다. 서버를 직접 만지실 수 없다면 쓰시는 도구를 먼저 보십시오. 구글도 “Blogger나 Shopify와 같은 플랫폼을 사용하는 경우 플랫폼에 이미 리디렉션 솔루션이 내장되어 있을 수 있습니다”라고 밝히고 있습니다.출처[1] Google 검색 센터 - 리디렉션 및 Google 검색

  • Apache: Redirect permanent "/old" "https://example.com/new"
  • NGINX: return 301 $scheme://example.com/about/service

자바스크립트로 거는 방법은 마지막 수단입니다. 자바스크립트 리다이렉트는 구글이 페이지를 그려 봐야 보이고, 그리기가 실패하면 그대로 묻히기 때문입니다.19[19]구글은 조건을 달아 둡니다. “서버 측 리디렉션 또는 meta refresh 리디렉션을 실행할 수 없는 경우에만 JavaScript 리디렉션을 사용하세요.” 이유도 함께 나와 있습니다. “Google에서는 Googlebot이 크롤링한 모든 URL을 렌더링하려고 시도하지만 여러 가지 이유로 렌더링이 실패할 수 있습니다. 따라서 JavaScript 리디렉션을 설정한 경우 콘텐츠 렌더링이 실패하면 Google에서는 그 리디렉션을 절대 알아채지 못할 수 있습니다.” 서버에서 거는 301은 응답 머리에 담겨 오므로 그릴 필요가 없고, 그래서 실패할 자리도 없습니다.출처[1] Google 검색 센터 - 리디렉션 및 Google 검색

국내 사이트라면 이유가 하나 더 있습니다. 네이버는 리다이렉트가 걸린 사이트의 소유확인을 301일 때만 보장한다고 명시합니다. meta refresh나 자바스크립트로 걸면 소유확인이 안 됩니다.20[20]네이버 고객센터의 문장은 “이러한 리다이렉트 사이트는 웹마스터도구에서 소유확인 되지 않으며, 웹 프로토콜(protocol) 표준인 301 리다이렉트일 경우에만 소유확인을 보장합니다”입니다. 같은 글은 meta refresh와 자바스크립트를 웹 표준이 아니라고, 301은 웹 표준을 지킨 것이라고 구분해 두었습니다. 구글은 meta refresh를 쓸 만한 대안으로 인정하는데 네이버는 아예 인정하지 않는 것입니다. 네이버에 사이트를 등록하실 때는 도착 주소로 하셔야 합니다.출처[9] 네이버 서치어드바이저 고객센터 - 301 리다이렉트(redirect) 설정 소개

무엇을 서버 설정 파일에 옛 주소를 새 주소로 보내는 301 한 줄을 넣습니다

안 하면 옛 주소로 들어온 고객과 검색엔진이 사라진 페이지에 그대로 도착합니다

확인 옛 주소를 브라우저에 넣어 새 주소로 바뀌는지 보고, 개발자 도구의 네트워크 탭에서 상태 코드가 301인지 봅니다

안 되어 있다면 서버를 만지실 수 없으면 쓰시는 플랫폼의 리다이렉트 기능을 찾으시고, 없으면 개발을 맡은 쪽에 301로 걸어 달라고 하시면 됩니다

홈으로 몰면 soft 404가 됩니다

옛 주소를 한꺼번에 홈페이지로 보내면 안 됩니다. 구글은 관련성이 떨어지는 단일 주소로 전부 보내면 soft 404로 처리될 수 있다고 밝히고 있습니다.21[21]구글의 문장은 “이전에 사용하던 여러 URL을 새 사이트의 홈페이지처럼 관련성이 떨어지는 단일 도착 URL로 전부 리디렉션하면 안 됩니다. 이러한 방법은 사용자에게 혼란을 야기하며, soft 404 오류로 처리될 수 있습니다”입니다. soft 404는 찾는 페이지가 없는데도 서버가 정상 응답을 돌려주어 구글이 내용 없는 페이지로 판단하는 상태를 말합니다. 그렇게 되면 옛 주소도 새 주소도 득을 보지 못합니다. 이 대목은 업계도 같은 말을 해서, 저희가 읽은 16곳 가운데 12곳이 대응하는 페이지로 보내라고 밝혔습니다.출처[2] Google 검색 센터 - 사이트 이동 방법(URL 변경이 있는 경우) 대응할 페이지가 없다면 홈으로 보내지 마시고 404를 돌려주시면 됩니다.

체인은 3개 이하로 두십시오

업계 글이 한도를 5개라고도 하고 10개라고도 하는데, 10홉은 크롤러가 따라가는 한도이고 권고가 3개 이하입니다.22[22]숫자가 셋인데 서로 다른 이야기입니다. 10홉은 크롤러가 따라가는 한도로, 구글 문서에 “기본적으로 Google 크롤러는 최대 10개의 리디렉션 홉을 따릅니다”라고 나와 있습니다. 3개 이하는 권고이고 사이트 이전 문서에 “3개 이하가 적당하며 최대 5개까지입니다”로 나옵니다. 업계가 많이 쓰는 5홉은 존 뮬러의 말인데, Search Engine Journal이 전한 원문에 “Search engines just follow the redirect chain (for Google: up to 5 hops in the chain per crawl attempt)“이라고 괄호가 붙어 있습니다. 한 번의 크롤 시도에서 따라가는 수라는 뜻입니다. 같은 답변에서 그가 말한 영향도 “the main effect is that it’s a bit slower for users”였습니다. 구글이 체인을 줄이라며 든 이유도 “사용자의 지연 시간이 늘어나며 일부 사용자 에이전트와 브라우저에서는 긴 리디렉션 체인을 지원하지 않습니다”이고, 링크 가치가 깎인다는 말은 없습니다. 희석을 쓴 곳은 16곳 중 5곳이었는데 근거가 한 단계당 15% 또는 5%를 가정한 계산뿐이었습니다. 유지 기간은 1년이 기준입니다

업계에 돌아다니는 180일은 서치 콘솔 주소 변경 알림의 효력 기간이고, 리다이렉트를 얼마나 둘지와는 다른 이야기입니다.23[23]180일이 나오는 자리는 서치 콘솔 도움말입니다. “Google 검색으로부터 트래픽이 계속 발생하면 리디렉션을 180일 이상 유지합니다”로 시작하지만 핵심은 그다음입니다. “180일이 지나면 Google은 기존 사이트와 새 사이트 간의 관계를 인식하지 못하며 기존 사이트가 크롤링이 가능한 상태로 계속 유지되는 경우 이 사이트를 관계없는 사이트로 취급합니다.” 주소 변경 알림으로 신호를 옮기는 작업도 이전을 시작한 후 180일간 계속된다고 나와 있습니다. 즉 180일은 도구의 효력 기간이고, 리다이렉트를 얼마나 둘지는 검색 센터의 1년 쪽을 따르시면 됩니다. 저희가 읽은 16곳에서 1년이라고 쓴 곳이 4곳, 180일이라고 쓴 곳이 3곳이었는데 둘을 구분한 곳은 없었습니다. 이 도구 자체는 도메인이나 하위 도메인이 바뀔 때만 필요하고, 같은 도메인 안에서 경로만 바꾸거나 HTTP에서 HTTPS로 옮길 때는 필요하지 않습니다. 무엇을 도메인이 바뀌는 이전이면 서치 콘솔에서 주소 변경 알림을 제출하고, 리다이렉트는 최소 1년 둡니다

안 하면 180일이 지나면 구글이 옛 사이트와 새 사이트의 관계를 더는 인식하지 못합니다

확인 서치 콘솔에서 새 주소의 색인 생성 보고서를 보고, 옛 주소가 “리디렉션이 포함된 페이지”로 잡히는지 봅니다

안 되어 있다면 경로만 바뀌었거나 HTTP에서 HTTPS로 옮긴 경우라면 이 도구는 필요하지 않으니 리다이렉트만 두시면 됩니다

직접 해 본 것

저희도 이 사이트에 301을 걸어 두었습니다. 2026년 10월 3일에 확인한 응답은 이렇습니다. 끝에 슬래시가 붙은 /blog/는 301로 /blog로 갑니다. 내려간 글 /blog/what-is-seo도 301로 /blog로 갑니다. 없어진 /thanks는 301로 홈으로 갑니다.

걸어 두고 한 가지를 배웠습니다. 301을 걸어 둔 주소를 나중에 다시 쓰면 리다이렉트가 새 글을 가로챕니다. 저희는 /blog/what-is-seo를 같은 슬러그로 다시 쓸 생각입니다. 그래서 설정 파일에 “같은 슬러그로 재발행하면 이 두 줄을 지울 것”이라는 메모를 밝혀 두었습니다.

자주 묻는 질문

301 에러는 무엇을 의미하나요?

301은 오류가 아닙니다. 주소가 영구히 옮겨졌다고 알리는 정상 응답입니다. 서치 콘솔이 옛 주소를 “리디렉션이 포함된 페이지”로 보여 주는 것도 정상이고, 색인은 도착 주소에만 생깁니다.24[24]서치 콘솔은 그 이유를 색인이 안 되는 항목 목록에 밝혀 둡니다. “URL이 다른 URL로 리디렉션됩니다. 리디렉션 URL은 색인이 생성되지 않으며 리디렉션 대상의 색인만 생성됩니다.” 옛 주소가 목록에서 빠지는 것이 정상 동작이라는 뜻입니다.출처[4] Search Console 도움말 - 페이지 색인 생성 보고서

301과 302의 차이점은 무엇인가요?

둘 다 다른 주소로 보내지만 구글이 받는 신호의 세기가 다릅니다. 301은 영구 이동이어서 검색 결과에 새 주소가 나오고, 302는 임시여서 옛 주소가 그대로 남습니다.25[25]구글이 임시 리디렉션을 쓸 자리로 든 예가 이해를 돕습니다. “사이트에서 제공하는 서비스가 일시적으로 사용할 수 없게 된 경우, 임시 리디렉션을 설정하여 현재 상황을 설명하는 페이지로 사용자를 리디렉션할 수 있습니다.” 이때 “검색 결과에 표시되는 원래 URL이 손상되지도 않습니다”라고 나와 있습니다. 점검 중이라는 안내로 잠시 보내는 자리가 302입니다.출처[1] Google 검색 센터 - 리디렉션 및 Google 검색 되돌릴 계획이 없다면 301을 쓰시면 됩니다.

리다이렉트는 무슨 뜻인가요?

들어온 주소에서 다른 주소로 자동으로 보내는 일입니다. 서버가 응답에 새 주소를 담아 보내고, 브라우저가 그 주소로 옮겨 갑니다.26[26]새 주소가 담기는 칸의 이름은 Location입니다. 규격은 “If a Location header field is provided, the user agent MAY automatically redirect its request to the URI referenced by the Location field value, even if the specific status code is not understood.”라고 설명합니다. 상태 코드를 몰라도 Location만 있으면 옮겨 간다는 뜻이라, 301인지 302인지는 사람 눈에 보이지 않습니다. 코드를 보시려면 개발자 도구의 네트워크 탭을 여셔야 합니다.출처[7] IETF RFC 9110 - HTTP Semantics 고객이 따로 누를 것은 없습니다.

더 볼 것

두 주소를 모두 열어 두신 채 대표만 정하셔야 한다면 301이 아니라 캐노니컬 태그가 맞습니다.27[27]구글은 대표 주소를 알리는 방법을 영향이 큰 순서로 늘어놓는데, 리디렉션과 rel=canonical이 모두 강력한 신호로 올라 있습니다. 둘의 차이는 세기가 아니라 하는 일입니다. 리다이렉트는 트래픽을 옮겨 옛 주소를 닫아 버리고, 캐노니컬은 두 주소를 모두 열어 둔 채 대표만 알립니다. 정렬이나 광고 추적 값이 붙은 주소처럼 고객이 실제로 들어오는 주소라면 닫으면 안 되니 캐노니컬을 쓰셔야 합니다. 저희가 읽은 16곳 가운데 이 구분을 따로 다룬 곳은 3곳이었습니다.출처[6] Google 검색 센터 - rel="canonical" 및 다른 메서드로 표준 URL을 지정하는 방법 주소를 옮기는 일 전체는 홈페이지 이전에서, 주소를 어떻게 짜는지는 URL에서 다룹니다.
